# Installing the patched kernel on FydeOS v23

Written for a MateBook E 2022 running FydeOS v23 (the `iris` image; `apu` and `slim` use
the same 6.12.54 kernel). Read the whole page before starting — the only step that can
brick the installation is writing to the wrong partition, and on this machine the obvious
candidate for "the EFI partition" is not the right one.

## 0. What is different about this build

The release string is **`6.12.54-01180-gb4e10020ba49-mbe`**, not the stock
`...-dirty`. This is deliberate:

* the modules install into `/lib/modules/6.12.54-01180-gb4e10020ba49-mbe/`, a directory
  that does not exist on a stock system, so nothing can overwrite the stock tree;
* `vermagic` contains `-mbe`, so **the two kernels and the two module trees cannot be
  mixed.** You must install `vmlinuz` and the modules together. Installing `i915.ko`
  alone on top of the stock kernel will simply fail to load the module.

There is no module-only install path. Either install both artifacts, or stay on stock.

## 1. Know your layout

Prerequisites: developer mode enabled and rootfs verification disabled
(<https://fydeos.com/question/enable-developer-mode/>,
<https://fydeos.com/docs/knowledge-base/getting-started/disable-rootfs-verification/>).
Without that `/` is read-only and nothing you put in `/lib/modules` survives a reboot.

```bash
sudo -i
lsblk -f
df -h /
```

On the MateBook E target the relevant devices are:

| Device | What it is |
|---|---|
| `/dev/loop0p3` | `ROOT-A`, ext2, label `ROOT-A`, 2.7 G, mounted at `/` — **only ~90 MB free** |
| `/dev/loop0p12` | `EFI-SYSTEM`, vfat, label `BFD1-C3FA` — **this is the FydeOS ESP** |
| `/dev/loop0p1` | `H-STATE`, ext4, the Android data partition |
| `/dev/nvme0n1p1` | OpenCore's own ESP. Mounted at `/tmp/grub_mnt` on some layouts. **Not FydeOS's** — writing `syslinux/vmlinuz.A` here does nothing. |

FydeOS v23 is a dual-boot image: the real root filesystems are partitions inside
`fydeos_dual_boot.img` on the `FYDEOS-DUAL-BOOT` partition, and the boot menu is
generated by `grub.cfg` with two entries, *A* and *B* (priority-selected with `cgpt`).
`grub` loads `dual_boot_ramfs.cpio` from the `FYDEOS-DUAL-BOOT` partition, which loop-mounts
the image, finds `p3` (A) or `p5` (B) and `switch_root`s into it.

So the file to replace is `<EFI-SYSTEM>/syslinux/vmlinuz.A`, and **`vmlinuz.B` is your
rollback path.** Confirm the mount point:

```bash
mount | grep -i -e esp -e BFD1
find /mnt /tmp -maxdepth 4 -name 'vmlinuz.A' 2>/dev/null
```

If `EFI-SYSTEM` is not mounted yet:

```bash
mkdir -p /mnt/esp
mount /dev/loop0p12 /mnt/esp
ls -l /mnt/esp/syslinux/
```

You should see `vmlinuz.A`, `vmlinuz.B`, `ldlinux.sys`, `root.A.cfg`, `default.cfg`. If
`vmlinuz.A` and `vmlinuz.B` have the **same** SHA-256, someone has already restored A and
you are on a pristine system:

```bash
sha256sum /mnt/esp/syslinux/vmlinuz.A /mnt/esp/syslinux/vmlinuz.B
```

## 2. Back up

```bash
mount -o remount,rw /
cp -a /mnt/esp/syslinux/vmlinuz.A /tmp/vmlinuz.A.backup
sha256sum /lib/modules/$(uname -r)/kernel/drivers/gpu/drm/i915/i915.ko \
    /tmp/vmlinuz.A.backup > /tmp/stock-sums.txt
```

Copy `/tmp/vmlinuz.A.backup` to a USB stick if you care about the install. You do **not**
need to back up `/lib/modules/$(uname -r)` — this build never writes there, and the stock
modules are on the read-only root image anyway.

## 3. Check the space budget first

`/` has ~90 MB free and the modules tree unpacks to roughly 85 MB. That is too tight to
do casually — an extract that runs out of space leaves a half-populated module directory,
which is worse than not installing at all.

```bash
df -h /
du -sh /home/chronos/user/Downloads 2>/dev/null
```

Free space until `/` shows **at least 120 MB** available; deleting the artifacts from
`Downloads` and trimming `/var/log` is usually enough. Keep the **archive** on the
stateful partition (`/mnt/stateful_partition`, where `~/Downloads` already lives) rather
than on `/`, but the extraction itself has to go to `/`:

```bash
tar -xzf ~/Downloads/modules-6.12.54-01180-gb4e10020ba49-mbe.tar.gz -C /
echo $?                 # must be 0 — do not continue if it is not
```

The top level of the tarball is `lib/modules/6.12.54-01180-gb4e10020ba49-mbe`, so this
adds one new directory and touches nothing else.

Check it landed where expected before touching the boot loader:

```bash
ls -d /lib/modules/6.12.54-01180-gb4e10020ba49-mbe
find /lib/modules/6.12.54-01180-gb4e10020ba49-mbe -name '*.ko' | wc -l
du -sh /lib/modules/6.12.54-01180-gb4e10020ba49-mbe
```

A complete install has **~900 `.ko` files** and roughly 85 MB (it is a full module set,
not just `i915`). Fewer than that means `tar` ran out of space.

If `tar` aborted, remove the partial directory, free space, and retry:

```bash
rm -rf /lib/modules/6.12.54-01180-gb4e10020ba49-mbe
```

## 4. Install the kernel

```bash
cd /home/chronos/user/Downloads     # or wherever you copied the artifacts
cp vmlinuz-6.12.54-01180-gb4e10020ba49-mbe /mnt/esp/syslinux/vmlinuz.A
sync
sha256sum /mnt/esp/syslinux/vmlinuz.A /mnt/esp/syslinux/vmlinuz.B
```

A and B now differ. **Do not touch `vmlinuz.B`, `root.B.cfg`, `ldlinux.sys` or
`ldlinux.c32`.**

A previous install also rewrote `root.A.cfg` and `default.cfg`; that is not part of the
kernel change and the stock contents of those files are not known here. If you have a
saved copy of them, restore it — they are the syslinux boot parameters for image A, and
`default.cfg` picks which entry boots.

## 5. Reboot and verify

The two patch markers are `drm_dbg_kms()` messages and do not print by default. Add
`drm.debug=0x4` to the kernel command line before rebooting if you want them at boot;
otherwise "the screen does not tear" is the evidence.

```bash
uname -r
# 6.12.54-01180-gb4e10020ba49-mbe

dmesg | grep -iE "Not touching native DSI|DSB not used for DSI"
```

* `Not touching native DSI GPIOs, keeping firmware state` ⇒ patch 1 is live
* `[CRTC:..] DSB not used for DSI output, falling back to MMIO` ⇒ patch 2 is live

To check without rebooting (only covers activity after the command — trigger a modeset
afterwards by switching VT or replugging an external display):

```bash
echo 0x4 > /sys/module/drm/parameters/debug
```

`drm.debug=0x4` is extremely verbose; drop it again once you have the lines.

Diagnostics:

* `uname -r` still shows `-dirty` → the old `vmlinuz.A` is still booting. Either
  `syslinux/vmlinuz.A` was written to the wrong ESP (see §1), or `default.cfg` points at
  another entry.
* `uname -r` shows `-mbe` but `lsmod` has no `i915`, or `dmesg` says
  `module verification failed` / `version magic ... should be ...` → the modules did not
  install where the kernel looks. Check
  `ls /lib/modules/$(uname -r)/kernel/drivers/gpu/drm/i915/` and redo §3.
* No `Not touching native DSI GPIOs` line and the screen still tears → the DMI entry did
  not match. Check `dmidecode -s system-product-name`; if it does not start with
  `MateBook E`, boot once with `i915.dsi_native_gpio_bypass=1` appended to the kernel
  command line.

## 6. Explicit toggles

Patch 1 exposes a module parameter, useful while testing:

```bash
i915.dsi_native_gpio_bypass=-1   # default: decide via DMI
i915.dsi_native_gpio_bypass=1    # always skip the native GPIO sequence
i915.dsi_native_gpio_bypass=0    # never skip (stock behaviour)
```

Patch 2 is unconditional and has no toggle — but note that the **stock** kernel already
accepts `i915.enable_dsb=0`, which disables the DSB path globally. That is the cheapest
way to test whether the DSB half of the fix matters on your panel, without writing
anything to disk:

```bash
# append to the kernel command line, reboot, look at the screen
i915.enable_dsb=0
```

## 7. Known limitations

* **Suspend/resume**: patch 1 keeps whatever panel state the firmware set up. After a
  suspend the panel may stay dark; a full reboot always recovers. If you need reliable
  resume, do not use this kernel.
* **Cold boot from a blanked panel**: same constraint — when the firmware has *not*
  powered the panel, skipping the GPIO sequence cannot power it on. On this machine the
  firmware does power it, so boot works; if you ever get a black screen after a CMOS
  reset or a BIOS update, boot image B.
* **The Android container**: this build re-implements the ChromiumOS subsystems the
  stock config enables (alt-syscall, esdfs, ashmem, uid_sys_stats, xt_quota2, `syscfs`
  accounting) so ARC keeps working. Those subsystems are 5.4-era code forward-ported to
  6.12 — they compile and are config-asserted, but they are the least tested part of the
  build. If the desktop works and the Android container does not, that is where to look.

## 8. Rollback

From the boot menu, select image **B**, then:

```bash
sudo -i
mount -o remount,rw /
cp -a /tmp/vmlinuz.A.backup /mnt/esp/syslinux/vmlinuz.A
rm -rf /lib/modules/6.12.54-01180-gb4e10020ba49-mbe
sync && reboot
```

Removing `-mbe` is all that is needed — the stock `6.12.54-01180-gb4e10020ba49-dirty`
tree was never modified.

If the machine will not boot at all: boot a FydeOS U-disk, mount the internal
`EFI-SYSTEM` (vfat, label `BFD1-C3FA`), and restore `syslinux/vmlinuz.A` from your backup.
Do not use the OpenCore ESP (`/tmp/grub_mnt` on the original layout) — it holds no FydeOS
kernel.
